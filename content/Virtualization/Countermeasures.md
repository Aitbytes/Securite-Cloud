With virtualization getting more attention from researchers, several solutions have been proposed to secure VM instances in Cloud Computing. These solutions range from preventing Side Channel Attacks to reducing the risk of achieving co-residency.

## Preventing Side Channel Attacks
We have seen that Side Channel Attacks are the main attack vector to bypass virtualization isolation features, thus many papers worked on detecting and preventing these attacks. In order to detect Cache-based Side Channel Attacks (CSCA), researchers exploit the significant features of CSCA such as high cache miss times, virtual CPU utilization, and virtual memory utilization. Another key feature of Side Channel Attacks is the use of high-resolution internal clock. Eliminating references to internal clocks will protect software from several SCA. Researchers also exploited the hypervisor's scheduler to reduce the overlapping execution time of any two VMs but this solution may reduce performances. Another approach injects noise inside the side-channel, increasing the error rate for malwares exploitng this side-channel. Preventing Side Channel Attacks can protect VMs from data leaks or other co-residency attacks. However, implementing these solutions is costly, as they require the cloud provider to make major modifications to their platforms.

## Preventing Co-Residency
The first step of every attack on a VM hosted on a cloud platform is to achieve co-residency between the target VM and a malicious VM owned by the attacker. Cloud providers may be able to mitigate these attacks by preventing attackers to achieve or to verify co-residency. We have seen multiple methods which allow a user to confirm co-residency with a target VM. CSCA can be exploited to verify co-location of two VMs but implementing solutions to prevent these attacks is costly for cloud providers. However, other verification methods can be prevented by confining information to the user. For example, we studied the use of the shared Dom0 IP to determine co-residency of VMs running on Xen hypervisor. Keeping information about this address a secret from user will ensure co-residency cannot be confirmed through this medium. This reduces the number of techniques available to the attacker who needs to resort to other methods that are more difficult to achieve. Alongside preventing co-residency verification, cloud providers can also increase the difficulty for an attacker to achieve or maintain co-residency. Cloud computing allows VMs to migrate between hosts, even during runtime, improving resource optimization by reducing the workload of stressed hosts. This service can be used as a tool to counter co-residency attack : following the Vickrey-Clarke-Groves (VCG) mechanism, the cloud platform performs a periodic migration of VMs, reducing the time window where two VMs are co-residents. However, continuously migrating VMs leads to a decrease in performance and an increase in power consumption. Another approach is to take co-residency into consideration when establishing the VMs allocation policy. This approach aims at reducing the probability of co-resident VM by working on the features which determine a VM's placement. When it comes to basic policies, the ones related to the Most VM policy seem to perform well against co-residency attacks, provided that the servers are correctly configured. Still, researchers developed new policies to reduce the risk of co-residency while keeping satisfying performances. An example of such a policy is the Co-location Resistance Algorithm, which opens a fixed number of servers and assigns the new VM to one of these servers at random. Another effective policy is Previously-selected-server-first (PSSF). This policy ensures that the servers that already host VMs from the user are considered first when the user creates a new VM. With this policy, in order to spread their VMs and achieve co-residency with the target, an attacker will need to create new accounts or to keep his VMs running, even if they failed to achieve co-residency.

## Hypervisor security
As the software responsible for managing and isolating VMs, improving hypervisors will help increase the security of VMs and hypervisors themselves. Several approaches have been taken to this end. Nested virtualization has been used to stack the hypervisor running the VMs on top of an host hypervisor. This host hypervisor will ensure the integrity of each VM and their data and will warn them of any breach of integrity. Another approach is to remove the hypervisor after initialization : the hardware enforce the isolation of VMs without hypervisor. This approach reduces the attack surface and remove other challenges of virtualization such as indirections. In addition to these solutions, VMs coalitons have been introduced as a tool for security. This hypervisor implements a mandatory access control (MAC) policy which defines groups of VMs who can share hardware and software resources. This can be implemented in two security policies : a Type Enforcement policy, which determines the VMs allowed to share their resources, and a Chinese Wall policy, which prevents VMs from conflicted types to run at the same time. Finally, we can distinguish two new types of hypervisors. The pure isolation hypervisor divides the machine into independent partitions, unable to share resources aside from CPU time and primary memory. These hypervisors are easy to implements but only useful for customers using large servers. The sharing hypervisor allows the sharing of resources, including files. This type implements a secure shared file store where a high-level partition will have read-only access to low-level data while a low-level data gets read-write access.
